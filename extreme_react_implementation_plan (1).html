極限Reactマルチプロファイル・アーキテクチャ移行計画書

管理オーバーヘッドを根絶し、スクラッチパッドと動的プロファイルに最適化された超堅牢Reactモードへの移行

1. 背景と基本方針

現在の multi_agent.py および orchestrator.py に実装されているワークフロー（計画生成・ジャンプ・非同期検証）は、予測不可能な開発現場の現実と衝突し、計画の修正そのもののバグによるスタックや、不要なトークン消費を招いていました。

本計画は、複雑なPythonコード側の状態遷移ロジックをすべて排し、実績のある純粋な対話型Reactループ（agent.py 内の run_stream）を主軸に据えます。AI自身がコンテキストに応じて脳内の役割（プロファイル）を自律的に切り替え、かつスクラッチパッドを毎ターン自己更新する「極限Reactマルチプロファイルモード」を安全に追加実装するための手順です。

2. コアシステムプロンプト (EXTREME_REACT_SYSTEM_PROMPT)

💡 脳内プロファイルの自己制御
外部インスタンスを分けるのではなく、単一の強力なReactコンテキスト内でAIに以下のマインドセットとスクラッチパッドの絶対遵守を義務付けます。 
# 役割と行動指針
あなたは、ソフトウェア開発におけるすべての工程（設計・実行・検証・記憶管理）を単独で臨機応変にこなす、超強力な自律型Reactエージェントです。
あなたはタスクの状況に応じて、自身の「マインドセット（プロファイル）」を脳内で動的に切り替えて行動してください。

## 脳内プロファイル
1. 【Architectモード】（設計・編集フェーズ）
   - コード設計やパッチ適用時。edit_fileやpatch_fileを主に使用。bash実行は極力避ける。
2. 【Operatorモード】（実行・テスト・検索フェーズ）
   - テストの実行やログ確認、外部検索時。run_bashやweb_search、run_pipelineを主に使用。
3. 【Scribeモード】（自己監査・記憶管理フェーズ）
   - ツール実行結果（Observation）を受けた直後、必ず進捗を整理し、update_scratchpadを実行する。

# 【最重要】スクラッチパッド（作業記憶）の絶対遵守ルール
あなたはツールを実行する前、または実行した直後に、必ず「update_scratchpad」ツールを呼び出して、自身の記憶を最新状態に同期しなければなりません。

スクラッチパッドは常に以下のフォーマットを厳持してください：
【現在の脳内プロファイル】（例：Operatorモード - テスト検証中）
【ゴール】全体の目標
【完了済み】これまでに確定した事実、書き換えたファイル、通ったテスト
【直面している課題・エラー】（スタックトレースの要約やコンフリクトの原因を克明に残す）
【次の具体的一歩】次に呼び出すべきツールとその目的

4. ExtremeReactOrchestrator の実装コード設計

状態管理ロジックを極限まで削ぎ落とした、バグの入り込む余地のないクラス設計です。

class ExtremeReactOrchestrator:
    def __init__(self, agent: OpenRouterAgent, auto_git: AutoGit):
        self.agent = agent
        self.auto_git = auto_git
        
    def run(self, user_prompt: str) -> str:
        # 1. 安全対策としてのディスク事前バックアップ
        backup_res = self.auto_git.backup(self.agent.cwd)
        
        # 2. システムプロンプトを「極限Reactマルチプロファイル用」へ上書き
        self.agent.set_system_prompt(EXTREME_REACT_SYSTEM_PROMPT)
        
        # 3. タスクの開始（Scratchpadの初期設定）
        self.agent.start_task(user_prompt)
        
        # 4. 全ツールを解放した実績のある純粋Reactループに制御を全面委譲
        final_answer = self.agent.run_stream(user_prompt)
        
        self.agent.end_task()
        return final_answer

5. 移行後のメリット・検証

  • 状態遷移バグの根絶: 複雑な分岐やGOTO、REPLANのPython実装を通らないため、制御側のバグによるハングアップやスタックが物理的に消失します。
  • 生コンテキストの維持: 伝言ゲームによる文脈劣化がなくなり、エラーログのスタックトレースを同じコンテキスト（脳内）で直接処理するため、バグ修正の命中率が劇的に向上します。
