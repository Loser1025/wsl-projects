動的ワークフロー刷新＆マルチモード統合 計画書

目的：足元バグの完全駆除、および「状態遷移マシーン型イベントループ駆動」への大一元化

1. 現状のバグ・設計欠陥の整理

現在のソースコードを再精査した結果、プランモード（固定グラフ型）とマルチモード（対話ReActループ型）の双方に、システムのクラッシュやハングを引き起こす深刻なバグが確認されました。

重大度：高

【マルチ】並列実行時の UnboundLocalError

orchestrator.py の並列実行関数 _par_exec 内で、キャッシュ非対象ツール（run_bash等）が呼ばれた際、キャッシュキー変数 ck が初期化されず通過するため、後半の登録処理で 100% UnboundLocalError が発生しクラッシュします。

重大度：高

【マルチ】空レスポンス時の不正なメッセージシーケンス

ReActループ内で空レスポンスを検知した際、content=None でかつ tool_calls を持たないアシスタントメッセージを配列に強引に挿入しています。これは OpenRouter/OpenAI API 規格に著しく違反するため、次ターンで 400 Bad Request エラーを誘発します。

重大度：高

【ワークフロー】親スレッドプール枯渇によるデッドロック

ジャンプバック（GOTO）処理関数 _do_goto が、親の with ThreadPoolExecutor as reviewer_pool: のスコープネスト下から再帰的に呼び出され、同じプールにレビュータスクを多重投入（submit）しています。アカウント数（n_accounts）が少ない環境下では高確率でスレッドが枯渇しハングアップします。

重大度：中

【記憶】ジャンプ・分岐時のコンテキスト汚染

WorkflowGraph でステップをジャンプバック・動的変更した際、Executor側の会話履歴（self.conversation）が一切巻き戻されず蓄積され続けます。古い文脈がコンテキスト窓を汚染し、LLMが「すでに作業を終えた」と錯覚して同じ失敗を繰り返す原因になります。

2. 動的ワークフロー（Dynamic Workflow）一元化アーキテクチャ

プランモード（Orchestrator）とマルチモード（対話型ReAct）を個別のクラス・別々のループとしてバラバラに管理する現在の設計を廃止し、「すべての処理を、実行時に組み立て可能な動的ステップとしてイベントループで駆動する」 状態遷移マシーン（Unified Engine）へと刷新します。

新・アーキテクチャ概要図

[ユーザー指示 (User Input)] │ ▼ [初期プラン生成 (Planner)] ──> 【 動的タスクキュー (Task Queue) 】 <───────┐ │ │ ▼ │ 【 状態遷移イベントループ (Event Loop) 】 │ (動的ステップの │ │ 追加・変更) ┌─────────────────────┼─────────────────────┐ │ ▼ ▼ ▼ │ [逐次/並列Executor] [対話モード(ReAct)] [検証 (Reviewer)] ───┘ (隔離ステート実行) (記憶のロールバック) (JITプラン変更判定) │ │ │ └─────────────────────┴──────────┬──────────┘ │ ▼ [一括ステート同期 (Join)] │ ▼ [最終報告 (Reflector)]

動的統合による3大コアメリット

  • JIT（Just-In-Time）プランニングの実現: 最初に長大なステップを固定化するのをやめ、各ステップの結果やステート、あるいはエラー内容に応じて、Plannerがその場で「次に最適なステップ」を動的に生成し、キューの先頭に割り込ませることが可能になります。
  • 「対話」のステップ化（Human-in-the-Loop）: マルチモードを独立したループにせず、InteractiveStep という1つの特別なステップとしてキューで扱います。自律解決が難しい状況や、ユーザーの承認が必要な場面では、エンジンが動的に対話ステップへ状態遷移します。
  • 安全な並列ステート管理（MapReduce型）: 並列ステップの実行中は各エージェントに隔離されたローカルステートを持たせ、同期（Join）した瞬間にメインスレッドが一括で共通ステートにマージすることで、レースコンディションを完全に排除します。

3. 段階的実装・修正タイムライン

Day 1 足元の致命的バグ駆除と防護ガードレールの設置
  • 並列実行関数 _par_exec で ck = None の初期化を行い、UnboundLocalError を完全解消。
  • 空レスポンスに対するメッセージシーケンスに "（思考中...）" などのプレースホルダを挿入し、APIエラーを防止。
  • pipeline.py の proc = None ガード、および agent.py の [DONE] 到達時の return 脱出を適用。
Day 2 制御シグナルの型安全化とエージェント履歴のチェックポイント化
  • -1 や "replan" などの混在を廃止し、明確な WorkflowSignal(Enum) を導入。
  • ステップ開始時点の executor.conversation のスナップショット（ディープコピー）を保持し、GOTOやルート変更発生時に記憶を過去のチェックポイントまで綺麗に巻き戻す「ロールバック機能」を実装。
Day 3 - 4 状態遷移マシーン型「統一動的グラフエンジン」への全面刷新
  • 固定の配列バッチ処理（bi = 0 から進むループ）を完全撤廃し、TaskQueue の監視によるイベントループ型へ移行。
  • 対話型ReActループ（マルチモード）を InteractiveStep としてキューへ統合。
  • 並列実行時のローカルステート隔離、および同期完了時の一括マージ処理を実装。
Day 5 統合シナリオテスト＆限界検証
  • 「プラン実行中に意図的にシェルエラーを発生させ、自律的に原因調査ステップを割り込ませた後、ユーザーに『対話モード』で確認を求め、指示を貰ったら動的に新しいルートを再構築して復帰する」という複合シナリオの結合テストを実施。

4. 制御シグナルとデータ構造の定義案

シグナル (Enum) パラメータ ワークフローエンジンの挙動
WorkflowSignal.CONTINUE なし 次のステップをキューから取り出して通常実行する。
WorkflowSignal.GOTO target_step_id: int 指定されたステップIDへ移動。会話履歴（記憶）を対象ステップ開始前の状態へロールバック。
WorkflowSignal.INSERT_STEPS new_steps: list[PlanStep] LLM（Planner）がJIT生成したリカバリ/追加ステップを、タスクキューの先頭に動的に Push する。
WorkflowSignal.INTERACTIVE context_prompt: str 自律実行を一時停止し、ユーザーの介入を求める InteractiveStep へ状態遷移する。
WorkflowSignal.ABORT reason: str 前提条件未達などの致命的失敗として、即座にAutoGitでのロールバックを視野に入れつつ全体を中断。
