🛠️ エージェントシステム・安全リファクタリング計画書

1. 修正の基本方針（ゴール）

  1. 既存機能の完全維持：update_scratchpad の義務化や、各種 Pipeline-First 検索ツール（smart_read など）の挙動、出力フォーマットは一切変更しない。
  2. 安全性の根本治療：自作エスケープによる shell=True (または bash -c) 依存を捨て、引数配列（list）による安全なプロセス起動へ移行する。
  3. リソースリークの撲滅：タイムアウト時の time.sleep によるメインブロッキングを排除し、非同期（asyncio）タスク制御を導入してゾンビプロセスを完全に封じ込める。
  4. グローバル状態の解消：エージェントの並行・マルチスレッド実行に耐えられるよう、状態（ステート）をインスタンス内部にカプセル化する。

2. 段階的リファクタリング・ロードマップ

一気に書き換えるとデバッグが困難になるため、影響度の低い部分から4つのフェーズに分けて安全に適用します。

Phase 1状態管理の分離（スレッドセーフ化）

【対象】 mimic_tui/tools.py
【目的】 マルチスレッドや並行処理が走った際に、履歴データやブラウザが競合してクラッシュするのを防ぐ。

  • アクション1：グローバルに置かれている _read_files_registry = set() を、OpenRouterAgent クラスの初期化（__init__）時に self.read_files_registry = set() として持たせるように変更。
  • アクション2：各ツールの関数（read_file や _check_read_warning）に、現在実行中の agent インスタンス、または session_id をコンテキストとして渡せるようにシグネチャを拡張。
  • アクション3：_pw_context（Playwright）の lazy init を行う _get_browser_page() 内に threading.Lock() による簡易的なセマフォ（排他制御）を導入。

Phase 2引数配列（List）化によるセキュリティ強化

【対象】 mimic_tui/tools_linux.py
【目的】 自作エスケープ関数（_shell_quote）に潜むシェルインジェクションやReDoSの脆弱性をロジックレベルで100%消滅させる。

  • アクション1：search_in_file および smart_read の subprocess.run 実装を、シェルを介さない配列形式に書き換える。
ロジックのリファクタリング例
# ✕ 修正前: shell=True や bash -c に依存（脆弱性リスクあり）
# subprocess.run(["bash", "-c", f"grep -n ... {_shell_quote(pattern)}"])

# ◯ 修正後: 引数を配列に分解（OSが直接バイナリを叩くため100%安全）
cmd = ["grep", "-n"]
if ignore_case:
    cmd.append("-i")
cmd.extend(["-C", str(context_lines), pattern, str(p.resolve())])

result = subprocess.run(cmd, capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=15)
効果： OSレベルで直接 grep バイナリが引数を受け取るため、LLMがどんな悪意ある文字列（'; rm -rf /; ' など）を出力しても、単なる「一つの検索文字列」として安全に処理されます。

Phase 3run_bash の非同期化（asyncio）とゾンビ撲滅

【対象】 mimic_tui/tools_linux.py
【目的】 タイムアウト時にメインスレッドを2秒間フリーズさせるバグを修正し、切り離された孫プロセスのリークを完全に防ぐ。

  • アクション1：run_bash を async def run_bash_async へとリファクタリング。
  • アクション2：time.sleep(2) を廃止し、asyncio.wait_for による非同期ブロッキング（他の並行処理を止めない待機）に差し替え。
  • アクション3：Linuxの preexec_fn=os.setpgrp を用い、タイムアウト検知時に os.killpg(proc.pid, signal.SIGKILL) を即座に実行するロジックを実装。
効果： タイムアウトが発生してもエージェントのシステム全体はミリ秒単位で動き続け、サーバーのメモリやプロセスを食いつぶすアンデッド（ゾンビ）プロセスが1つも残らなくなります。

Phase 4関数の責任分離とUI/UXの二重承認プロンプト解消

【対象】 mimic_tui/tools.py
【目的】 edit_file が失敗した際に勝手に patch_file を呼ぶことで発生する「二重承認（同じ確認ボタンを2回押される）」というUXバグと、コードの意図しない破壊を防ぐ。

  • アクション1：edit_file 内で old_string が見つからなかった場合（count == 0）、下層ツールに処理を丸投げするのをやめ、LLMへの明確なエラー返却に変更する。
責任を明確にするロジック修正
# ✕ 修正前: 勝手に横流しして二重承認プロンプトを発生させる
# if count == 0: return warning + patch_file(...)

# ◯ 修正後: LLMにエラーを突き返し、次のツールの選択権を委ねる
if count == 0:
    return (
        f"エラー: 指定された 'old_string' がファイル内に見つかりません。\n"
        f"現在のファイル内容を `search_in_file` や `smart_read` で再確認し、正確な文字列でやり直すか、"
        f"インデントのズレが疑われる場合は、最初から `patch_file` ツールを明示的に指定して実行してください。"
    )
効果： 人間は1回の変更につき1回だけ承認ボタンを押せば良くなり、エージェントが「厳密な置換」に失敗した際に、裏で勝手に「曖昧なパッチ」を当ててコードをバグらせる危険性をゼロにできます。

3. リグレッション（機能崩壊）を防ぐためのテスト計画

修正によって「賢さ」や「Pipeline-Firstによるコンテキスト節約」が失われていないかを確認するため、以下の3段階の結合テストを行います。

  1. コンテキスト節約テスト：大きなファイルをターゲットにしてわざと read_file を実行させ、システムがこれまで通り「5,000文字以上の警告」を出し、LLMが自律的に smart_read や search_in_file へと手数を切り替えられるかを確認する。
  2. ファジーパッチテスト：インデントが少しズレたコードブロックを用意し、最初から patch_file を指定して実行させ、difflib やインデント正規化によって正しくコードが修正されるか（既存のファジー性能が生きているか）を確認する。
  3. 無限ループ・タイムアウトテスト：run_bash で yes コマンドや sleep 100 などの終わらないコマンドを実行させ、指定秒数でメインシステムを巻き込むことなく確実にプロセスが抹殺され、リソースが解放されるかを実証する。

4. 総括

このリファクタリング計画は、既存の洗練されたツール群や「Pipeline-First」という素晴らしいエージェントの頭脳（ロジック）には一切手を加えず、それを支える土台（Pythonのプロセス制御・セキュリティ・状態管理）だけを鉄骨からコンクリートへと補強する設計になっています。

これを適用することで、24時間365日、マルチユーザー環境で安全に自動開発をこなし続ける最強のプロダクションシステムへと進化を遂げることができます。
