1. アーキテクチャの基本設計（全体像）

現在のシングルエージェント（OpenRouterAgent）構造を、役割ごとのインテリジェンスに分解します。コード内やシステムプロンプトで特定の商用モデル名を明言せず、構成（Config）から動的に推論プロバイダやパラメータを注入できる「疎結合マルチエージェント」へと刷新します。

ユーザーが対話するフロントエンド（現在の TUI 画面および main.py のインターフェース）は一切変更せず、既存の「Pipeline-First」による優れたコンテキスト節約機能をそのまま継承します。

2. エージェントの役割定義とツールカプセル化

すべてのエージェントは抽象クラスを継承し、各自の役割（Role）に最適化された最小限のツールセットのみを所有します。

エージェント役割（Role） 担当業務 割り当てツール モデル要件（抽象定義）
設計担当 (Architect) タスクの分解、パッチ作成、リポジトリマップの把握 get_repo_map, edit_file, patch_file 高論理推論、長文脈対応モデル
執行担当 (Operator) 環境構築、テスト実行、コードベース検索、Webブラウズ run_bash, smart_read, grep_codebase, web_search, fetch_webpage 低遅延、コード・コマンド生成特化モデル
記憶担当 (Scribe) コンテキストのリアルタイム状態管理、記憶の圧縮 update_scratchpad, search_history 高速処理、格安・構造化出力最適化モデル

3. 段階的リファクタリング・実装コード案

Step 1 agent.py: 役割ベースの抽象化とカプセル化

モデル指定を引数で抽象化し、特定のAIベンダー名に依存しない基底クラスを定義します。

mimic_tui/agent.py の刷新案
# 役割ベースのエージェント共通基底クラス
class BaseRoleAgent:
    def __init__(self, config, tools_registry, role_description: str):
        self.config = config              # モデル名やコンテキスト長を内包する抽象設定
        self.tools = tools_registry        # 各自に制限されたツールレジストリ
        self.role_description = role_description
        self.conversation = []

    def _init_system_prompt(self, base_prompt: str):
        self.conversation.append({
            "role": "system",
            "content": f"You are an expert AI agent specializing in: {self.role_description}.\n{base_prompt}"
        })

class ArchitectAgent(BaseRoleAgent):
    """設計・ファイル修正の責任を持つエージェント"""
    pass

class OperatorAgent(BaseRoleAgent):
    """非同期プロセス実行とWeb探索の責任を持つエージェント"""
    pass

class ScribeAgent(BaseRoleAgent):
    """作業記憶の維持・自動圧縮（コンパクション）の責任を持つエージェント"""
    pass

Step 2 orchestrator.py: 非同期でのAI間協調ループ

orchestrator.py は単一の ReAct ループを回すのをやめ、エージェント間のメッセージルーティングとAI間セルフデバッグの制御に特化させます。

mimic_tui/orchestrator.py の刷新案
class MultiAgentOrchestrator:
    def __init__(self, architect: ArchitectAgent, operator: OperatorAgent, scribe: ScribeAgent):
        self.architect = architect
        self.operator = operator
        self.scribe = scribe
        self.max_auto_retries = 3

    async def execute_task_loop(self, user_prompt: str) -> str:
        # 1. 記憶担当から現在のコンテキスト（スクラッチパッド）を読み込み
        current_memory = self.scribe.get_memory()
        
        # 2. 設計担当が解決プランを立案
        plan = await self.architect.plan_solution(user_prompt, current_memory)
        
        retry_count = 0
        while retry_count < self.max_auto_retries:
            # 3. 執行担当が非同期環境でプランを実行（テスト・検証）
            result = await self.operator.execute_and_verify(plan)
            
            if result.is_success:
                break
                
            # 【AI間セルフデバッグ】失敗時は執行担当のエラーログを設計担当へ直接フィードバック
            log.warning(f"タスク失敗。設計担当に再プランを要求します。試行: {retry_count + 1}")
            plan = await self.architect.replan(plan, result.error_output)
            retry_count += 1
            
        if retry_count >= self.max_auto_retries:
            return f"⚠️ 自律復旧上限に達しました。ユーザーの介入が必要です。最終エラー:\n{result.error_output}"

        # 4. タスク完了後、またはターン毎に記憶担当が動的に記憶圧縮を実行
        await self.scribe.compact_and_save(result.summary)
        
        return result.final_output

Step 3 tools.py: 完全書き換え式スクラッチパッドの保護（要約ロジック）

ツールが特定のエージェント（記憶担当）を呼び出せるよう、引数を経由してコンパクションロジックを統合します。文字数オーバー時にデータを機械的に切断（[:800]）して破壊するのを防ぎます。

mimic_tui/tools.py の 3番（自動要約）ロジック統合
def update_scratchpad_smart(content: str, scribe_context: Optional[ScribeAgent] = None) -> str:
    """既存のインターフェースを維持しつつ、文字数超過時は記憶担当に自動圧縮を委譲する"""
    if len(content) <= 800:
        set_scratchpad(content)
        return "✓ スクラッチパッドを更新しました。"
        
    if scribe_context is None:
        # 記憶担当が不在の場合の安全なフォールバック（前方切り捨てによるデータ構造破壊を防止）
        set_scratchpad(content[:800])
        return "⚠️ スクラッチパッドの文字数制限（800文字）を超過したため、末尾が切り捨てられました。"
        
    log.info("スクラッチパッドの上限超過を検知。記憶担当による自動圧縮を実行します。")
    
    # 記憶担当エージェントの軽量モデルに「ゴール、完了、制約」の抽出を非同期で依頼
    compacted_memory = scribe_context.call_compaction_pipeline(content)
    
    set_scratchpad(compacted_memory[:800])
    return "✓ スクラッチパッドが上限に達したため、重要な制約とゴールを維持したまま高密度に自動要約されました。"

4. アーキテクチャ刷新に伴うトレードオフ評価

🚀 進化するメリット：
  • ハルシネーションの劇的な低減：設計（Architect）とテスト実行（Operator）の脳を分離することで、お互いが「相互レビュー」の関係になり、コードのデプロイ成功率が跳ね上がります。
  • モデル切り替えによるコストの最適化：記憶の整理（Scribe）やファイル検索（Operator）に安価で高速な軽量モデルを割り当て、真に難しい設計の瞬間だけ最高峰モデル（Architect）にバトンを渡すため、API費用を大幅に削減できます。
  • 安全ブレーキの確立：AI同士のデバッグループが停滞した場合、オーケストレーターが検知して人間の「承認ハンドラー」へ安全に制御権を戻すため、APIの無限ループ消費（破産リスク）を未然に防げます。
⚠️ 発生するデメリットと対策：
  • 会話オーバーヘッド（遅延）の増加：エージェント間でメッセージが往復するため、シングルエージェントと比較してターンごとの初期応答にわずかな遅延が発生します。➔ 対策：OperatorとScribeには最速クラスのモデルを設定することで体感速度を維持します。
  • 関数の単一責任性の低下：ツールがエージェントのコンテキスト（scribe_contextなど）を一部知る必要があるため、関数の独立性がやや下がります。➔ 対策：引数へのデフォルト値 None の設定を徹底し、ツール単体テストの容易性を担保します。
