1. 全体像

mimic_tui のコンテキスト管理は、LLM の有限なコンテキストウィンドウ（トークン上限）を効率的に使い切るための多層防御システムです。API 呼び出し前の事前チェック、会話履歴の自動圧縮、ツール出力のキャッシュ、エラー時の自動リカバリなど、複数のレイヤーで構成されます。

2. 定数・設定 (config.py)

コンテキスト管理の中核をなす定数とモデル別コンテキスト長の設定です。

2.1 グローバル定数

_CHARS_PER_TOKEN
= 4
日本語/英語平均: 1トークン ≈ 4文字。文字数→トークン換算の基本係数。
_COMPACTION_RATIO
= 0.75
コンテキスト容量の 75% に達したら圧縮を実行するしきい値比率。
_COMPACTION_DEFAULT
= 3,000,000 (文字)
context_length が不明 (0) の場合のフォールバック圧縮しきい値。
MAX_TOOL_ROUNDS
= 60
ReAct ループの最大ターン数。tool_calls が継続する回数の上限。
_THINK_BUDGET_CHARS
= 15,000 (文字)
<think> タグ内の思考がこの文字数を超えるとストリームを強制停止。無限思考防止。
MAX_RETRIES
= 5
API リトライ最大回数。コンテキスト超過・サーバーエラー時にリトライ。
BASE_BACKOFF / MAX_BACKOFF
= 2.0s / 60.0s
指数バックオフの基本/最大待機時間。リトライ時に適用。
_OVERHEAD_CACHE_TTL (agent)
= 1.0s
system_prompt + context_header のオーバーヘッド計算をキャッシュする TTL。

3. アーキテクチャ

mimic_tui のコンテキストは 3 つのレイヤーで管理されます。

┌───────────────────────────────────────────────────────────────────┐ │ ① System Prompt 層 (毎ターン自動構築) │ │ ┌─────────────────────────────────────────────────────────────┐ │ │ │ system_prompt (ユーザ設定) │ │ │ │ + context_header (CWD + Scratchpad) │ │ │ │ + task_context (現在のタスク目標) │ │ │ └─────────────────────────────────────────────────────────────┘ │ ├───────────────────────────────────────────────────────────────────┤ │ ② Conversation 層 (履歴メッセージリスト) │ │ ┌─────────────────────────────────────────────────────────────┐ │ │ │ self.conversation = [user, assistant, tool, user, ...] │ │ │ │ ↑ API ペイロードの "messages" リストを構成 │ │ │ └─────────────────────────────────────────────────────────────┘ │ ├───────────────────────────────────────────────────────────────────┤ │ ③ 永続化層 (外部記憶) │ │ ┌────────────────┐ ┌──────────────┐ ┌─────────────────────────┐ │ │ │ Scratchpad │ │ ReactLog │ │ past sessions (/search) │ │ │ │ (セッション内) │ │ (JSONL/MD) │ │ (セッション横断注入) │ │ │ └────────────────┘ └──────────────┘ └─────────────────────────┘ │ └───────────────────────────────────────────────────────────────────┘

3.1 メッセージ構造

API に送信されるメッセージはすべて OpenAI ネイティブ形式（role: system / user / assistant / tool）を使用します。内部的なマーカー（_skip_save など）は API 送信前に自動除去されます。

role用途追加フィールド
systemsystem_prompt — モデルの指示content (str)
userユーザー入力・ツール実行結果の報告content (str)
assistantAI の応答・ツール呼び出し指示content (str, nullable), tool_calls (list)
toolツール実行結果tool_call_id (str), content (str)

3.2 コンテキスト容量の計算

# 圧縮しきい値 (文字数)
compaction_threshold_chars = context_length × 4 × 0.75
# context_length が 0 の場合は 3,000,000 文字をフォールバック

# 実際に会話に使える文字数 (TTL=1.0s でキャッシュ)
effective_threshold = compaction_threshold_chars - len(system_prompt) - len(context_header)

# API 送信時の最大文字数 (90%)
max_api_chars = context_length × 4 × 0.90
available_for_messages = max_api_chars - len(system_prompt)

4.2 _build_context_header() — コンテキストヘッダー構築

毎 API 呼び出し時に自動生成され、system role の位置ではなく user メッセージに注入されます。

def _build_context_header(self) -> str:
    sep = "─" * 40
    return (
        f"[作業フォルダ] {self.cwd}\n"
        f"{sep}\n"
        f"--- [エージェントの自己記憶（Scratchpad）] ---\n"
        f"{get_scratchpad()}\n"
        f"--- [Scratchpad ここまで] ---"
    )

4.3 _task_context() — タスクコンテキスト

start_task(goal) で設定されたゴールが存在する場合に注入されます。

def _task_context(self) -> str:
    if not self._task_goal:
        return ""
    return f"[現在のタスク] {self._task_goal}"
Scratchpad (自己記憶) の仕組み
Scratchpad はセッション中にエージェントが自分自身の作業記録を残すメモ領域です。 フォーマット: 【ゴール】【完了済み】【次のステップ】【発見事項】の4項目。 毎ターン get_scratchpad() で読み取り、context_header に含めて API に送信されるため、 エージェントは前のタスクの記憶を「覚えていなくても」常に参照できます。 最大 2000 文字に切り詰められ、前タスクの記憶を引き継ぐ設計です。

5. AgentOrchestrator のコンテキスト管理 (orchestrator.py)

Plan-and-Execute モードでは、Planner / Executor / Reflector の3つのエージェントが個別の会話履歴を持ち、それぞれにコンテキスト制限が適用されます。

5.1 Planner のコンテキスト管理

Planner はタスクをステップに分解する役割で、ツールを持ちません。 過去の (prompt, JSON) ペアを履歴に残すことで「JSON 崩れ」を自然に防ぎますが、 履歴が長すぎるとコンテキストを圧迫するため動的に制限します。 

def _max_planner_history(self) -> int:
    """Planner が保持する会話履歴の最大ターン数をコンテキスト長から計算。
    128K tokens → 8ターン, 1M tokens → 20ターン (線形スケール)"""
    ctx = self.planner._config.context_length
    if ctx <= 0:
        return 8
    return max(8, min(ctx // 50_000 * 2, 20))
履歴上限超過時: planner.conversation = planner.conversation[-max_planner_history:] で古いターンを切り捨て。 パース失敗時2ターン分をロールバック (conversation = conversation[:-2]) して再試行。

5.2 Reviewer のコンテキスト管理

Reviewer は Executor の出力結果を検証するエージェントです。結果の文字数を動的に制限します。

def _review_result_max_chars(self) -> int:
    """128K tokens → 2000文字, 1M tokens → 8000文字"""
    ctx = self.executor._config.context_length
    if ctx <= 0:
        return 2000
    return max(2000, min(ctx * _CHARS_PER_TOKEN // 500, 8000))

5.3 Executor 間でのコンテキスト節約

Executor に渡すプロンプトには「直近3件までの完了済みステップ結果」のみを注入します。

# _execute_step() 内
prior_done = [s for s in all_steps if s.index < step.index and s.result]
if prior_done:

        f"  Step {s.index} 「{s.description[:60]}」→ {s.result[:300]}"
        for s in prior_done[-3:]  # 直近3件のみ

5.4 最終まとめ時のトークン節約

全ステップ完了後のまとめプロンプトでは、最新5ステップ × 500文字にトリミングします。

_trimmed_results = [r[:500] for r in results[-5:]]
summary_prompt = (
    f"以下のタスクが完了しました。結果を簡潔にまとめてください。\n\n"

6. トリム・圧縮メカニズム

6.1 _compact_if_needed() — 会話の自動圧縮

ReAct ループの各ターン開始時に呼び出されます。現在の会話文字数が effective_threshold を超えている場合に実行。

圧縮前の conversation (例: 30 メッセージ) ┌─────────────────────────────────────┐ │ [0] user: タスク説明 │ ← 最初のペア (保持) │ [1] assistant: 了解 │ ← 最初のペア (保持) │ [2] user: ツール結果A │ ← 削除 │ [3] assistant: 思考... │ ← 削除 │ ... │ ← 削除 │ [28] user: 最近の結果 │ ← keep_recent (保持) │ [29] assistant: 思考... │ ← keep_recent (保持) └─────────────────────────────────────┘ ↓ 圧縮後 ↓ ┌─────────────────────────────────────┐ │ [0] user: タスク説明 │ ← 最初のペア │ [1] assistant: 了解 │ ← 最初のペア │ [user] "[26件の古い会話を削除 │ ← 削除通知 │ しました（コンテキスト節約）]" │ │ [assistant] "了解しました。" │ ← 確認応答 │ [28] user: 最近の結果 │ ← keep_recent │ [29] assistant: 思考... │ ← keep_recent └─────────────────────────────────────┘

keep_recent の値はコンテキスト長に応じて動的計算されます。

def _compaction_keep_recent(self) -> int:
    """小さいコンテキスト → 最低4, 大きい → 最大20"""
    return max(4, min(20, self.compaction_threshold_chars // 4000))

6.2 _trim_to_fit() — 送信前トリム

API 送信直前に、ペイロードがコンテキスト窓の 90% 以内に収まるまで繰り返しトリムします。

def _trim_to_fit(self, messages) -> list:
    max_chars = int(ctx * _CHARS_PER_TOKEN * 0.90)  # 90% 上限
    available = max_chars - len(system_prompt)
    total = sum(_msg_char_count(m) for m in messages)
    trim_count = 0
    while total > available and len(messages) > 4 and trim_count < 8:
        messages = _trim_messages_smart(messages)
        total = sum(_msg_char_count(m) for m in messages)
        trim_count += 1
最大8回までトリムを繰り返し、4メッセージ以下には削減しません。

6.3 _trim_messages_smart() — スマートメッセージ削除

最初の2メッセージ（system + 最初のuser）を保護し、body の25%を削除対象とします。

削除優先順位: 1. role="tool" のメッセージ (ツール実行結果) → 直前の assistant+tool_calls も一緒に削除 (孤立防止) 2. それでも足りない場合 → 残りから順に削除 保護対象: - messages[:2] (最初の2メッセージは絶対に削除しない) - 最低4メッセージは保持 (_trim_to_fit の条件)

6.4 _repair_message_sequence() — メッセージ修復

不完全な tool_calls / tool ブロックを除去し、API エラーを防止します。

  • 孤立 tool_calls: assistant が tool_calls を発行したが、対応する tool 応答が揃っていない → ブロックごとスキップ
  • 孤立 tool 結果: tool メッセージの直前が tool_calls を持つ assistant でない → 除去

10. エラーハンドリングとコンテキスト

10.1 _handle_api_exception() — API 例外処理

API 呼び出しで例外が発生した場合の分岐ロジックです。

例外発生 │ ├── RateLimitError (429) │ └── バックオフ待機 → リトライ (メッセージ変更なし) │ ├── ServerError (5xx) / OpenRouterAPIError (4xx) │ │ │ ├── コンテキスト超過判定 (_is_context_exceeded) │ │ └── trim_count < 5 なら _trim_messages_smart → リトライ │ │ │ ├── 401/403 → リトライ不可、再送出 │ │ │ └── その他 → バックオフ待機 + トリム → リトライ │ └── 接続エラー (RemoteDisconnected, ConnectionReset, Timeout) └── バックオフ待機 → リトライ (メッセージ変更なし)
